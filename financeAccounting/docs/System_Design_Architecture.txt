Part II – System Design & Architecture

System Architecture

The system follows a four-layer architecture designed to separate concerns and enable modular development. The Client Layer consists of the browser rendering Laravel Blade templates with Alpine.js for interactivity, Chart.js for graphical representations, and html2pdf.js for PDF export functionality, alongside API clients and external integrations accessible via Postman. The Application Layer contains all routing definitions including web routes in web.php, API routes in api.php, and authentication routes in auth.php, all protected by the AuthMiddleware which validates user sessions before allowing access to any financial module. The Controller Layer is organized by module with dedicated controllers for each functional area. The Accounts Payable module uses PaymentController and SupplierBillController. The Procurement module uses PurchaseOrderController, GoodsReceiptController, and MatchingController. The General Ledger module uses ChartOfAccountsController and JournalEntryController. The Financial Reporting module uses FinancialReportController, ManageDataController, and TaxComplianceController. Additional controllers include ARController, SalesTransactionController, DashboardController, and API controllers consisting of DemoDataController, ManagementBudgetController, and ProcurementForAPController. The Service Layer contains the core business logic extracted from controllers for reusability and testability. AccountPayableService handles supplier bill approval, payment processing, batch payments, and GRN completion. FinancePostingService manages automatic posting of AP payments, AR receipts, and inventory adjustments to the General Ledger. FinancialReportService computes income statements, balance sheets, cash flow statements, and budget vs actual reports directly from GL data. DashboardService aggregates KPI data from all modules for real-time visualization. The Data Layer uses Eloquent ORM models including SupplierBill, Payment, and Attachment for AP, PurchaseOrder and GoodsReceivedNote for Procurement, ChartOfAccount, JournalEntry, and JournalEntryLine for GL, ComputedFinancialReport, BudgetVsActual, and TaxRecord for Financial Reporting, SalesTransaction, Customer, and Invoice for Sales and AR, and Inventory and InventoryTransaction for Inventory. The Database Layer uses MySQL with tables organized by module. The technology stack uses PHP 8.3+ with Laravel 13.x framework, MySQL 8 for ACID-compliant storage, Tailwind CSS 4.3.3 for styling, Alpine.js 3.x for interactivity, Chart.js for charts, html2pdf.js for PDF generation, and Vite 8 for asset bundling. The Procure-to-Pay workflow demonstrates the complete module interaction sequence where a Purchase Order is created in Procurement, a Goods Received Note references the PO upon receipt, a Supplier Bill is created referencing both PO and GRN, 3-Way Matching compares all three documents, Approval moves the bill to Approved status, Payment processes the bill, and the payment is auto-posted to GL which updates Financial Reports and the Dashboard. The API architecture exposes RESTful endpoints under the /api/* prefix handled by dedicated API controllers returning JSON responses.

Database Schema

The database contains 16 active tables organized by module with specific relationships and design principles. In the Accounts Payable group, the supplier_bills table serves as the core AP document storing bill_no as a unique identifier, po_no and grn_no as cross-references to procurement documents, supplier name, amount, total_paid for tracking partial payments, due_date for aging calculations, status with values Pending, Approved, or Paid, matching_status with values Matched or Unmatched, ewt_rate for Expanded Withholding Tax computation, payment_terms, approved_at, and paid_at timestamps. This table has no direct foreign keys to procurement tables as it uses human-readable code references for flexibility. The payments table stores payment transactions against supplier bills with supplier_bill_id linking back to the bill, amount supporting partial payments, payment_method, payment_date, reference number, and notes. It auto-creates journal entries through the service layer. The attachments table provides polymorphic file attachment capability using attachable_type and attachable_id columns to link files to any model in the system. In the Procurement group, the purchase_orders table stores PO records with po_no as unique identifier, supplier, item_name, qty, unit_cost, amount calculated as qty multiplied by unit_cost, order_date, expected_delivery, and status tracking the lifecycle from Draft to Sent to Confirmed to Delivered to Cancelled. This table is referenced by the goods_received_notes table. The goods_received_notes table stores GRN records with grn_no as unique identifier, purchase_order_id as a foreign key to the referenced PO, supplier_bill_id as a foreign key to the linked bill, supplier, item_name, qty_ordered copied from the PO, qty_received entered at receipt, amount calculated as qty_received multiplied by unit_cost, received_date, and status. In the General Ledger group, the chart_of_accounts table maintains the complete account hierarchy with account_id as primary key, account_code for structured numbering, account_name, normal_balance indicating Debit or Credit, type classifying accounts as Asset, Liability, Equity, Revenue, or Expense, parent_account_id for self-referencing hierarchical relationships, and status for active or inactive accounts. The journal_entries table stores entry headers with journal_entry_id as primary key, transaction_date, reference_no as a unique identifier, description, and status indicating Draft or Posted. The journal_entry_lines table stores individual line items for each journal entry with line_id as primary key, journal_entry_id linking to the header, account_id linking to the chart of accounts, debit and credit amounts enforcing double-entry accounting where total debits must equal total credits, and line description. In the Financial Reporting group, the computed_financial_reports table stores pre-computed report data with report_type identifying the report, period_start and period_end defining the reporting period, label and section for report organization, amount, debit, credit, and sort_order for display ordering. This table is populated by the FinancialReportService. The budget_vs_actuals table tracks budget targets against actual amounts per account with account_id linking to the chart of accounts, budget_amount, actual_amount, and variance_amount. The tax_records table stores tax compliance data with reference_type and reference_id for polymorphic linking, tax_type, taxable_amount, tax_rate, tax_amount, tax_period, and filing_status. In the Sales and AR group, the sales_transactions table records sales orders with order_no as unique identifier, customer_name, total_amount, payment_method, status, is_posted_to_finance flag, and journal_entry_id linking to the posted GL entry. The customers table stores customer master data. The invoices table tracks customer invoices for AR with invoice_number, type, invoice_date, due_date, subtotal, vat_amount, total, and status. In the Inventory group, the inventories table stores item master data with item_name, sku as unique identifier, description, quantity, unit_cost, selling_price, category, and status. The inventory_transactions table records stock movements with inventory_id linking to the item, type indicating in or out, quantity, unit_cost, total, and polymorphic reference_type and reference_id to link back to source documents. Key design decisions include using polymorphic attachments through a single table serving all modules, code-based cross-references using human-readable PO, GRN, and Bill numbers for easy identification, auto-increment primary keys for performance optimization, status-driven workflow with a status column on every transactional table to track lifecycle state, and no cascade deletes to maintain audit trail integrity for all financial data.

Module Specification

The Accounts Payable module manages supplier bill processing, 3-way matching, approval workflow, and payment execution. Its specific tasks include creating supplier bills with references to purchase orders and goods received notes, executing 3-way matching by comparing PO amounts against GRN amounts against Bill amounts to ensure accuracy, managing the bill approval workflow from Pending status through Approved to Paid status, processing full and partial payments against approved bills, executing batch payments across multiple selected bills simultaneously, auto-posting completed payments to the General Ledger through journal entries debiting Accounts Payable and crediting Cash, attaching supporting documents to bills through the polymorphic attachment system, computing Expanded Withholding Tax based on configurable rates, and tracking payment due dates for aging analysis. The module uses PaymentController and SupplierBillController, models SupplierBill, Payment, and Attachment, and the AccountPayableService containing all business logic.

The Procurement module manages the purchasing lifecycle from purchase order creation through goods receipt. Its specific tasks include creating and managing purchase orders with item details, quantities, and costs, tracking the PO lifecycle through Draft, Sent, Confirmed, Delivered, and Cancelled statuses, recording goods received notes against POs upon physical receipt of items, automatically calculating GRN amounts based on quantity received multiplied by unit cost, linking GRNs to supplier bills for the matching process, and updating inventory quantities upon goods receipt. The module uses PurchaseOrderController, GoodsReceiptController, and MatchingController with models PurchaseOrder and GoodsReceivedNote.

The General Ledger module maintains the chart of accounts and manages all journal entries. Its specific tasks include maintaining a hierarchical chart of accounts with parent-child relationships supporting account types for Asset, Liability, Equity, Revenue, and Expense, creating double-entry journal entries with validation ensuring total debits equal total credits, posting journal entries to make them immutable in the ledger, auto-posting AP payments as Debit 2100 Accounts Payable and Credit 1010 Cash, auto-posting AR receipts as Debit 1010 Cash and Credit 4000 Revenue, auto-posting inventory adjustments to the appropriate accounts, generating trial balances, and exporting the chart of accounts and journal entries to PDF. The module uses ChartOfAccountsController and JournalEntryController with models ChartOfAccount, JournalEntry, and JournalEntryLine, supported by the FinancePostingService.

The Financial Reporting module generates comprehensive financial reports from General Ledger data. Its specific tasks include computing the Income Statement by grouping revenue account credits and expense account debits to calculate Net Income, generating the Balance Sheet showing Assets equal to Liabilities plus Equity, producing the Cash Flow Statement with Operating, Investing, and Financing activities sections, comparing Budget versus Actual amounts per account with variance calculations, generating Tax Compliance reports with EWT tracking and filing status, exporting all reports to PDF format, and managing budget data through the API. The module uses FinancialReportController, ManageDataController, and TaxComplianceController with models ComputedFinancialReport, BudgetVsActual, and TaxRecord, supported by the FinancialReportService.

The Accounts Receivable module tracks customer invoice payments and generates aging reports. Its specific tasks include displaying an AR overview with total receivables and collected amounts, tracking received payments against customer invoices, generating AR aging reports categorized by Current, 1 to 30 days, 31 to 60 days, 61 to 90 days, and over 90 days past due, and auto-posting AR receipts to the General Ledger. The module uses ARController.

The Sales module records sales transactions and manages customer invoicing. Its specific tasks include creating sales transactions with customer information, total amounts, and payment methods, tracking payment status as Pending or Paid, posting sales to finance for GL integration, and managing customer invoice records. The module uses SalesTransactionController with models SalesTransaction, Customer, and Invoice.

The Inventory module tracks inventory items, stock levels, and inventory movements. Its specific tasks include maintaining item master data with names, SKUs, quantities, costs, and selling prices, recording stock in and out transactions linked to source documents, auto-posting inventory adjustments to the General Ledger, and integrating with GRN for automatic stock increases upon goods receipt. The module uses models Inventory and InventoryTransaction.

The Dashboard module provides real-time business intelligence and KPI visualization. Its specific tasks include displaying KPI cards showing total expenses, total revenue, overdue bills count, overdue amount, and pending payments, generating revenue versus expense trend charts on a monthly basis, producing cash flow visualization charts, listing recent financial entries from all modules, and showing upcoming and overdue bill alerts. The module uses DashboardController and DashboardService.

The Authentication module secures system access with session-based authentication. Its specific tasks include handling user login and logout, validating sessions through AuthMiddleware on all protected routes, and controlling access at the route level. The module uses AuthController and AuthMiddleware with the User model.

The API module exposes RESTful endpoints for external integrations. Its specific tasks include loading demo data for testing and demonstration, managing budget records through CRUD operations, and providing procurement data for AP integration. The module uses DemoDataController, ManagementBudgetController, and ProcurementForAPController.

Integration Blueprint

All modules are designed to integrate with each other through defined service layer interactions, ensuring coordinated data flow across the entire ERP system. The integration matrix shows that AP integrates with Procurement through the 3-way matching process, with GL through payment auto-posting, and with the Dashboard by supplying KPI data. Procurement integrates with AP by providing PO and GRN data for bill creation, with Inventory by updating stock levels upon goods receipt, and with the Dashboard by supplying procurement KPI data. GL integrates with Financial Reporting by providing journal entry data for report computation, with the Dashboard by supplying GL balance data, and receives auto-posting from AP, AR, Sales, and Inventory modules. Financial Reporting reads GL data to compute reports. AR integrates with GL through receipt auto-posting, with Sales by creating invoices from sales transactions, and with the Dashboard. Sales integrates with GL through finance posting and with AR through invoice creation. Inventory integrates with Procurement through GRN linking for stock updates and with GL through adjustment posting. The Dashboard reads data from all modules to present aggregated KPIs.

The first major integration is the Procure-to-Pay 3-Way Matching between Procurement and AP. In this integration, the Procurement module creates a Purchase Order with amount calculated as quantity multiplied by unit cost. The Goods Received Note is created referencing the PO with amount calculated as quantity received multiplied by unit cost. The AP module creates a Supplier Bill referencing both the PO number and GRN number. The MatchingController then compares the PO amount against the GRN amount against the Bill amount. If all three amounts match exactly, the bill's matching_status is set to Matched. If any discrepancy exists, the status is set to Unmatched with notes describing the variance, requiring manual review. This ensures that the organization only pays for items that were actually ordered and received.

The second integration is AP Payment to GL Posting handled by the FinancePostingService. When a payment is created against an approved supplier bill, the AccountPayableService calls the posting service which automatically creates a journal entry in the General Ledger. The entry debits Account 2100 Accounts Payable by the payment amount and credits Account 1010 Cash by the same amount. The journal entry reference number stores the payment ID for complete traceability. This integration is executed synchronously within the same database transaction to ensure that if the GL posting fails, the payment is also rolled back, maintaining data integrity. Validation ensures debits equal credits and that the accounts are active.

The third integration is GRN to Inventory Stock Update between Procurement and Inventory. When a Goods Received Note is created with a quantity received value, the system locates the inventory record matching the item name and increases its quantity by the received amount. An InventoryTransaction record is created with type set to in to provide a complete audit trail. This integration is executed synchronously within the same request, ensuring inventory levels are always accurate. Validation requires the item to exist in the inventory master data and the quantity to be positive.

The fourth integration is Sales to AR Invoice Creation. When a sales transaction is recorded with customer information and total amount, the system automatically creates an invoice record in the Accounts Receivable module referencing the sales transaction. This ensures that every sale generates a corresponding receivable entry. Validation requires the customer to exist in the customer master data and the amount to be positive.

The fifth integration is AR Receipt to GL Posting. When an AR payment is received, the FinancePostingService creates a journal entry debiting Account 1010 Cash and crediting Account 4000 Revenue. This completes the revenue recognition cycle from sales through AR to the General Ledger. Validation ensures debits equal credits.

The sixth integration is Inventory to GL Adjustment Posting. When an inventory transaction is recorded, the FinancePostingService creates a journal entry for the inventory value adjustment, ensuring inventory changes are reflected in the financial statements. Validation requires the inventory account to exist in the chart of accounts.

The seventh integration is GL to Financial Reporting. The FinancialReportService queries journal entry lines joined with the chart of accounts to compute financial reports. Revenue accounts are summed by their credit balances for the income statement. Expense accounts are summed by their debit balances for the income statement. Asset and Liability accounts are balanced for the balance sheet. The computed results are stored in the computed_financial_reports table for caching and quick retrieval. Validation ensures report periods do not overlap and the GL is balanced.

The eighth integration is Dashboard Data Aggregation where the DashboardService runs aggregated queries across all modules. It reads supplier_bills for total expenses and overdue counts, sales_transactions for total revenue, payments for monthly totals, computed_financial_reports for chart data, and all status-based fields for KPI card values. This provides management with real-time visibility into the organization's financial position.

The complete Procure-to-Pay end-to-end integration sequence flows as follows. A Purchase Order is created in the Procurement module. Upon physical receipt of goods, a Goods Received Note is created referencing the PO. The supplier sends an invoice which is recorded as a Supplier Bill in AP referencing both the PO and GRN. The 3-Way Matching process compares all three documents for consistency. Once matched, the bill is approved by authorized personnel. Payment is processed against the approved bill, which triggers automatic posting to the General Ledger. The GL update then flows into the Financial Reports and Dashboard, providing complete visibility from procurement through payment.

Error handling strategies are defined for each integration point. If a GL account is not found during AP to GL posting, the payment is aborted and the transaction is rolled back with a logged error. If a bill is already matched, the system prevents duplicate matching and displays the existing match status. If an inventory account is missing in the chart of accounts during inventory to GL posting, the GL posting is skipped and queued for manual intervention. If module data is unavailable for the dashboard, empty states are shown with warning logs. If a database connection failure occurs at any point, the entire transaction is rolled back and a user-friendly error message is displayed.

Data synchronization rules ensure consistency across the system. AP Payments to GL Posting is always synchronous within the same database transaction following an all-or-nothing approach. GRN to Inventory Update is synchronous within the same HTTP request. Sales Posting to GL uses a flag-based approach with an is_posted_to_finance field that can be retried if the initial posting fails. Financial Reports are computed on-demand from live GL data and can be refreshed at any time. Dashboard KPIs are computed on each page load, pulling real-time data directly from the database.
